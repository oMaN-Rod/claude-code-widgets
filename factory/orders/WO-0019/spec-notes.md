# Spec notes: WO-0019 Strays (third spec, after the second send-back)

No blocking fault. The five design findings of the second inspection are answered: `stop` waits only on its own `$` calls (A6); hooks only set `isQueued` and one `$.clock.every(1000)` timer in `sync` runs the refreshes; the facts timeout is 45000 with 15000 kept for listing and kill; Live waits two turns before the first stop and says what each answer means; no module-level map. Checked in the 2.1.289 types: `TimerCall = (ms, fn: () => void) => Timer`, `Timer.cancel()`, `HookBudget.ms` 10 000 with `next` and `$` calls free (a `$.clock.sleep` is not: never use it to wait), `ProcessRunInit.timeoutMs` (default 30 s, ten minutes at most), and the reference's "Work that outlives a dispatch" naming `$.clock.every`. 94 lines, 15 acceptance lines. The earlier notes 1 to 15, as the two builds settled them, still stand; do not undo them. Settle these while rebuilding.

1. Two facts calls at once. `stop` on a row runs its own `born` check whatever is in flight, so a refresh's PowerShell and stop's can run side by side; the first build measured that as the slow case. The 45 s timeout is what makes it safe: give stop's facts call the same 45000, not 15000, and keep it to the one pid by key.
2. A refresh applies its result to the state as it is when it ends, not as it was when it began. `stop`, `forget` and `clear` may have removed a row or emptied the card while the listing was out; the refresh must not put that row back or overwrite `seen` with an older copy. Read `watch` again after every `await`.
3. Off then on while a refresh is in flight. Switching off blanks `watch` (so `isBusy` is false), switching on queues a new one, and the old refresh may end while the switch is on again and write stale rows. "Ends after the switch went off writes nothing" must hold for that case too: mark each `open` (a counter inside `watch`, not a module-level `let`) and let a refresh from an older `open` change nothing, and not clear the newer refresh's `isBusy`.
4. `stop` with `seen` null can only happen with `isQueued` or `isBusy` true (open sets it), so it answers `Still checking ports`. Keep that order; never let stop's own refresh be the one that takes the baseline for a port the person is asking about without the store rows being restored first, as Refresh step 2 says.
5. The timer callback returns at once (`void tick($).catch(...)`); nothing in it may be awaited by the engine. A tick that throws before `isBusy` is set must not leave `isBusy` true; a tick whose refresh rejects clears it in the `finally`. After `open` on a reload `isBusy` is reset, which is right only because the old environment's work is gone: say so in a comment.
6. Windows facts script. Terms still describes one filtered query per process with the first build's figures (37 s, 3 s); line 5 gives the second build's 11.4 to 12.4 s for the slim whole-table form. Keep the form the machinist measured as fastest with the same argv and the same output lines; put the measured time of the shipped script in the build log.
7. `Still checking ports; try stop 47613 again in a moment.` is 54 characters and an answer, not a card row, so nothing to fit; but it must name the port the person typed without the leading `:`.
8. After a successful stop the pair stays in `seen`, so the second stop answers `Nothing` at once. On POSIX a survivor of a plain `kill` therefore never returns (earlier note 2): keep the second build's listing after the kill and its `kill was sent but :PORT is not seen free` answer, as stop's own `$` calls.
9. A6 and A5 need a listing that never answers. Make it a promise the test holds and settles later, not a rejected one, and prove with the recorded argv that no second `netstat` or `lsof` started.
10. Demo: "drawn after the engine's clock has run one tick past the request" depends on `render.ts` and `docs/engine.js` firing `clock.every`. If they do not, the rest frame is the empty sentence, which the spec allows; say in the build log which it is. The stand-ins are still the director's.
11. Live: the first stop's own facts call can take 12 s or more; if `live.ts` moves on before it answers, the two stops' answers arrive out of order. Read by sentence, as the spec says, and log the chain and `host` if the first answer is `Nothing`.
